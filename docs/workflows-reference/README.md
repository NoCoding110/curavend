# Curavend — Complete Workflow Reference

A technical catalog of **every workflow in the Curavend platform**, extracted directly
from the source (`packages/api` routes/services/crons/queues + `packages/web` features +
`packages/db` schema). Each workflow entry records its actors, trigger, entry points
(frontend page + `METHOD /api/...` endpoints), permission/tenant scope, step-by-step flow,
state machine (with exact enum values quoted from code), side effects, and source files.

> **How this differs from `docs/training/`** — the `training/` (help‑center) docs are
> task‑oriented guides for end users (52 feature pages, 23 how‑to recipes, 6 persona
> quickstarts). This `workflows-reference/` set is the *exhaustive technical map*: it
> documents **all 201 workflows** including the many internal, automated, and
> integration flows that have no help‑center page.

## ⚠️ Discrepancy findings from this documentation pass

Documenting against the real code surfaced gaps between the *intended* design and the
*implemented* behaviour. These are **observations only — no code was changed** during
documentation. Items marked ✅ were independently re‑verified against source.

1. ✅ **Pricing chain is 2‑tier, not 4‑tier.** `routes/pricing.ts:7` resolves
   `CONTRACT → MEDICARE → null`. The 5‑tier cascade (CONTRACT → GPO → FEE_SCHEDULE →
   MEDICARE → MANUAL) exists only as a comment in `lib/contractPricing.ts`. `catalog.ts`
   overlay does CONTRACT → LIST; `spendCalculator.ts` does STATE → CUSTOM → MEDICARE.
   Three live paths disagree. *(03)*
2. ✅ **Epic write‑back is not auto‑wired.** `DocumentReference`/`Procedure` write‑back
   (W7‑06/W7‑07) is exposed only via manual `POST` routes; `queues/orderEvents.ts` does
   **not** import `createDocumentReference`/`createProcedure`, so the "auto‑push on
   order completion" the service comments describe never fires. *(07)*
3. **Order `send-for-approval` is effectively a no‑op** — both ternary branches resolve
   to `NEW_ORDER`. *(02)*
4. **Approvals path bypasses queue events** — `approvals.ts` approve/reject mutate
   sub‑status but never enqueue `order.status_changed`, so ERP push + notifications are
   skipped on that path (unlike `orders.ts`/`encounter.ts`). *(02)*
5. **Order sub‑status enum drift** — `PUT /orders/:id/status` doesn't validate input;
   handler/queue still recognise legacy values (`VENDOR_CONFIRMED`, `DISPENSED`,
   `SPEND_CONFIRMED`) absent from the 10‑value schema enum. No `SHIPPED` sub‑status. *(02)*
6. **`GET /api/transfers/suggestions`** is described in the file header but **no handler
   is registered**. *(06)*
7. **Item‑master hygiene** exposes read/diagnose reports only — no merge mutation
   endpoint despite the "merge duplicates" framing. *(06)*
8. **`RECALL_STATES.INVESTIGATING`** is defined but never set by any transition. *(06)*
9. **Auto‑resolution invoice‑match rules (W4‑17)** expose a `/preview` decision but are
   not invoked by the 3‑way‑match run — preview‑only today. *(04)*
10. **Possible missing tenant/object guards** (auth‑only, no per‑tenant check) flagged on:
    `hospital-vendors` writes, `gpo/resolve-rate`, `spend-calculator`, `invoices/import-payments`,
    several `consignment`, `dme-rental-periods`, `dme-documents`, and `clinical-templates`
    (no role gate) endpoints. Worth a dedicated security review — see the per‑file Notes
    sections. *(03, 04, 05)*
11. **Mixed admin‑gate convention** — most routes gate on `role === ACCOUNT_MANAGER*`;
    `hospitals`/`departments`/`facilities`/`forecasting` gate on `userType === 'ADMIN'`. *(06)*
12. **`externalFulfillment` webhook operates on `labOrders`**, not supply `orders` — do
    not conflate with the supply‑order lifecycle. *(02)*
